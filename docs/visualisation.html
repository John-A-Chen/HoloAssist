01 — Client Quick Start

Required hardware

  • Meta Quest 3 headset, paired controllers, charged. Developer mode enabled.
  • USB-C cable for the Quest (build and run from Editor)
  • Linux laptop running Ubuntu 22.04 with ROS 2 Humble installed.
  • Logitech Brio 4K (or any UVC webcam / Intel RealSense) for AprilTag cube perception.
  • Printed 36h11 AprilTags on 40 mm cubes (tag IDs 10–33, four cubes). Refer to the perception documentation for details.
  • UR3e + OnRobot RG2 on the robot router (192.168.0.194) or URSim in Docker (192.168.56.101).

Required software

  • Unity 6.3 LTS (6000.3.9f1) with Android Build Support module installed (OpenJDK + SDK + NDK).
  • Meta XR SDK 85.0.0 and all packages listed in Software stack — installed via Unity Package Manager when the project first opens.
  • ROS 2 Humble + the project's ros2_ws built (colcon build --symlink-install).

Step 1 — Clone & open the Unity project

# Repository root
git clone git@github.com:John-A-Chen/HoloAssist.git
cd HoloAssist
git checkout demo

Open Unity/My project/ in Unity Hub. The first import is slow, it will take several minutes.

Step 2 — Open the demo scene

In the Project window navigate to Assets/Scenes/SampleScene.unity and open it. This is the only scene used for the demo.

Step 3 — Start the ROS side

# From repo root, in a fresh terminal
source /opt/ros/humble/setup.bash
source ros2_ws/install/setup.bash

# Fake hardware + perception + dashboard
./launch.sh --perception --dashboard

# OR — URSim + full stack (need URSim Docker running on 192.168.56.101)
./launch.sh --robot-ip 192.168.56.101 --fake-gripper --perception --moveit --dashboard

Note the WiFi IP printed by the launcher — this is what Unity needs.

Step 4 — Connect Unity to ROS

In Unity Editor open Robotics - ROS Settings. Set:

  • ROS IP Address: the laptop WiFi IP from Step 3.
  • ROS Port: 10000.

On the robot router subnet (192.168.0.x) the in-scene ROSAutoConnect component will discover the host automatically. On any other network (uni WiFi, phone hotspot) disable it and enter the IP manually.

Step 5 — Deploy to Quest 3

  1. Connect the Quest to the laptop via USB-C, accept the "Allow USB debugging" prompt inside the headset.
  2. Unity - File - Build Profiles - ensure Android is the active platform.
  3. Click Build And Run. APK installs to the Quest and launches.

What success looks like

  • Quest passthrough shows the physical room with a UR3e holographic twin anchored at the trolley.
  • Cube holograms appear within 1–2 seconds of pointing the Brio at a printed cube face.
  • The RobotHUD floats in front of the operator showing mode + joint angles + EE pose.
  • Holding the left primary button (X) opens the radial menu; selecting a mode switches RMRC / Direct Joint / Hand Guide.
  • Right stick moves the arm; right trigger drives the gripper.
02 — Purpose and Role

Subsystem 4 is the operator's window into HoloAssist. The Quest 3 scene is rendered by Unity here, and Subsystem 4 is responsible for everything in that scene except the digital twin and manual control core — those are owned by Subsystem 3 (Nic). S4 anchors S3's twin in the workspace and wraps it with cube and bin holograms, floating panels, a radial menu, the task / sorting UI, environment themes, and the passthrough toggle. The operator's mode switches and trigger inputs are routed through S4's UI layer into S3's RobotController, which publishes the actual velocity / gripper commands.

What the operator sees

  • A live UR3e digital twin + ArticulationBody joint mirroring Subsystem 3 (Nic)
  • AR cube holograms at the positions detected by perception (AprilTag-based, relayed onto /holoassist/unity/cube_N_pose).
  • A floating RobotHUD with mode, joint angles, EE pose, EE lock, gripper state.
  • A grab-and-place RobotInfoPanel with the full diagnostic readout.
  • A RadialMenu on the left primary button: mode switching (RMRC Translate/Rotate, Direct Joint, Hand Guide), passthrough toggle, environment cycling, task control, confetti / banner, etc.
  • BinDetector trigger zones with a BinStatusPanel counter; TaskConfigPanel sets target count / completion mode; TaskTracker scores correct vs wrong sorts.
  • PassthroughToggle swaps between MR (passthrough) and full VR (skybox + virtual environment).
  • EnvironmentCycler swaps decorative theme roots (e.g. Portal Chamber / grass / open room).
  • JointTFVisualizer + TFAxisMarker overlay coordinate axes on each link for debugging.

How Subsystem 4 supports the other subsystems

  • Perception (S1, John) — Subsystem 4 visualises the cube poses S1 publishes. The cube hologram smoothing (averaging, jitter rejection, persistOnTagLoss) is owned here so perception jitter doesn't ruin the AR experience.
  • Autonomous (S2, Oliver) — The TaskConfigPanel is the operator-facing entry point. Task mode (FixedTarget / OneOfEach / OneOfEachClass) drives how completion is scored; tags on perception-spawned cubes (ObjectClass) flow into TaskTracker.
  • Digital Twin + Manual Control (S3, Nic) — Nic owns the URDF-imported UR3e, the ArticulationBody hierarchy, JointStateSubscriber, RobotBasePlacer, and RobotController (the script that publishes velocity / gripper commands). S4 sits on top: the radial menu, EE lock, sub-mode toggle, and gripper trigger are S4's UI / input layer, and they call into Nic's RobotController. S4 makes Nic's twin and controller usable inside the headset; Nic owns the twin's correctness and the control publisher.

06 — Main Scripts

Each card lists the file, attached GameObject (if known), responsibilities, the key Inspector fields, and the failure mode if misconfigured.

CubePoseSubscriber

Path
Assets/Scripts/CubePoseSubscriber.cs
Attached
Dedicated GameObject (commonly named CubePoseSubscriber)
Responsibility
Subscribes to {topicPrefix}/cube_N_pose for N=1..cubeCount; transforms pose into Unity space relative to robotBase; spawns and animates a prefab per cube with smoothing, averaging, outlier rejection, and (optionally) tags spawned cubes with an ObjectClass for the task system.
Key fields
topicPrefix (default /holoassist/unity), cubeCount (4), robotBase (Transform — MUST be set), cubePrefabs[], poseTimeout (3 s), persistOnTagLoss (false legacy / true preferred), smoothing (0.5), useAveraging (true), positionAverageWindow (6), rotationAverageWindow (3), outlierRejectDistance (0 = off), tagSpawnedCubes, cubeClassNames[], cubeIsGood[], autoAddCollider (true)
Inputs
ROS PoseStamped messages on the topic prefix.
Outputs
Cube GameObjects in the scene; ObjectClass tag on each (when enabled).
Breaks if
robotBase unset - cubes spawn at world origin. Wrong topicPrefix - no messages received. Missing topic_tools relay on ROS side - no messages on /holoassist/unity/cube_N_pose.

RobotHUD

Path
Assets/Scripts/RobotHUD.cs
Attached
"RobotHUD" GameObject
Responsibility

Key fields
controller (RobotController ref), distanceFromCamera (1.5 m), offset ((0.3, -0.12, 0)), followSpeed (2.5), followCamera (true), panel size, colours, tfVisualizer, passthroughToggle

Outputs
Camera-relative 3D text panel.
Breaks if

PanelPlacer

Path
Assets/Scripts/PanelPlacer.cs
Attached
Any panel GameObject (HUD, InfoPanel, TaskConfigPanel, BinStatusPanel, CoachingPanel, RobotDataPanel)
Responsibility
Adds a BoxCollider + Rigidbody + XRGrabInteractable to make the panel grabbable with the XR rays. On grab, flips the panel's followCamera flag (for panels that have one) instead of disabling the MonoBehaviour — so live data keeps flowing while the panel is being moved.

Outputs

BinDetector + BinStatusPanel + TaskTracker + ObjectClass

Paths
Assets/Scripts/BinDetector.cs, BinStatusPanel.cs, TaskTracker.cs, ObjectClass.cs
Responsibility
BinDetector is a trigger zone on each bin (auto-builds container walls); ObjectClass tags each cube (className + isGood); when a cube enters a bin trigger TaskTracker.OnSort is called and scores it; BinStatusPanel renders one row per bin.
Key fields

Path
Assets/Scripts/HeadsetStreamPublisher.cs

07 — Data Flow and Integration

The bridge is bidirectional. Robot state and perception poses flow into Unity for display; operator input flows back out as velocity / gripper commands to drive the robot.

┌─ Perception (S1, John) ────────────┐ ┌─ Robot Driver / MoveIt (S2 / S3) ──┐ │ AprilTag + cube_pose │ │ ur_robot_driver + controllers │ │ /holoassist/perception │ │ /joint_states │ │ /april_cube_N_pose │ │ /tcp_pose_broadcaster/pose │ └──────────────────┬─────────────────┘ └──────────────────┬─────────────────┘ │ │ │ topic_tools relay │ │ │ │ /holoassist/unity/cube_N_pose │ │ │ └────────────────────┬────────────────────┘ │ ▼ ros_tcp_endpoint (TCP :10000) │ ▼ ┌────────────── Unity / Quest 3 (Subsystem 4) ───────────────┐ │ │ │ ROS-TCP-Connector (v0.7.0) │ │ │ │ │ ├── JointStateSubscriber (S3) ──► ArticulationBody │ │ │ (digital twin, S3)│ │ ├── RobotHUD / RobotInfoPanel ──► TextMeshPro │ │ │ (mode, joints, EE)│ │ ├── CubePoseSubscriber ──► Cube hologram │ │ │ (smoothed, anchored) │ │ │ │ │ Operator input (XR controllers + RadialMenu) │ │ │ │ │ └── RobotController (S3 — manual control) │ │ │ │ │ ├──► /forward_velocity_controller/commands │ │ └──► /finger_width_controller/commands │ │ │ │ In-Unity loop (no ROS): │ │ BinDetector → TaskTracker → BinStatusPanel / │ │ EventBanner / │ │ ConfettiBlaster │ └────────────────────────────────────────────────────────────┘ │ ▼ Quest 3 operator view (passthrough + holograms + UI)

Integration touch-points

  • Inbound from S1 (perception): AprilTag-detected cube poses, relayed onto Unity-friendly topic names by topic_tools relay on the ROS side. Subsystem 4 owns the smoothing / averaging / persistence logic that shapes the raw feed into a stable AR hologram.
  • Subsystem 3 (Nic — digital twin + manual control): Nic's JointStateSubscriber consumes /joint_states (~500 Hz URSim) and drives the ArticulationBody twin; RobotBasePlacer anchors the twin; RobotController consumes the operator's controller input that S4's radial menu / EE-lock / sub-mode UX routes to it, and publishes /forward_velocity_controller/commands + /finger_width_controller/commands. S4's RobotInfoPanel also subscribes to /tcp_pose_broadcaster/pose directly to show EE pose.
  • No direct ROS link to S2 (autonomous).

09 — Running and Testing

Run these in order. Each test isolates one capability so a failure points at one place.

Test 1 — Unity Editor, no ROS

Purpose
Confirm the project opens, packages resolve, and the scene plays without errors.
Steps
Open SampleScene.unity - press Play.
Expected
No compile errors. Console shows ROSConnection trying to connect (and failing — that is fine). UI panels render in front of the Editor camera. Radial menu canvas exists but is hidden.
Evidence
Screenshot of Editor in Play mode with no Console errors.
Troubleshoot
Compile errors - missing ROS2 scripting define - add it to Standalone Player Settings. Package errors - re-import via Window - Package Manager.

Test 2 — Unity Editor with live ROS

Purpose
Confirm the bridge is up and joint states stream in.
Steps
Start ./launch.sh --perception --dashboard in a terminal. Set the ROS IP in Unity. Press Play.
Expected
Launcher terminal logs Connection from <ip> + several RegisterSubscriber + RegisterPublisher entries. Robot arm in scene mirrors URSim / real pose. ros2 topic hz /joint_states reports ~500 Hz.
Evidence
Terminal log + screenshot of arm moving in Unity.
Troubleshoot
No connection - wrong IP, firewall blocking 10000/tcp (sudo ufw allow 10000/tcp). Arm static - joint_states not publishing, External Control not playing on URSim.

Test 3 — Quest 3 build & run

Purpose
Confirm the APK builds and the headset runs the demo.
Steps
Quest connected via USB, developer mode on. File - Build And Run. Watch the build log + adb logcat -s Unity:* in another terminal.
Expected
APK installs, app launches automatically, headset shows the scene with passthrough on.
Evidence
Quest screen recording or photo through the lens.
Troubleshoot

12 — Limitations and Assumptions

Confirmed limitations (from code)

  • ROSAutoConnect only scans 192.168.0.101–110. Disabled in scenarios outside the robot router.
  • CubePoseSubscriber transforms poses through a single robotBase Transform — there is no multi-arm support.
  • PanelPlacer's "flip followCamera" pattern only works on panels that expose the field. RobotDataPanel, BinStatusPanel, CoachingPanel still use the legacy "disable script" path; they will freeze on grab.
  • HeadsetStreamPublisher JPEG payloads can exceed the ROS-TCP bridge buffer; the component must be disabled for some tests.
  • TaskTracker is a singleton with no persistence — every Editor Play restarts state from zero.

Assumptions

  • The laptop and Quest are on the same WiFi network with no AP/client isolation.
  • Perception is publishing /holoassist/perception/april_cube_N_pose and a topic_tools relay is bridging it to /holoassist/unity/cube_N_pose (one process per cube).
  • The ROS side already has hand-eye calibration loaded so cube poses are in base_link frame, not camera_color_optical_frame.
  • The UR3e is mounted on the trolley facing 180° from the URDF default.
  • Subsystem 3 (Nic) owns the digital twin and manual control core: the URDF-imported UR3e, RobotController, JointStateSubscriber, and RobotBasePlacer are present in the scene, current with the demo branch, and not duplicated.

Future improvements

  • Add followCamera to BinStatusPanel, CoachingPanel, RobotDataPanel for full PanelPlacer-safe coverage.
  • Add Inspector tuning for minMoveDistance, snapDistanceThreshold, useSmoothDamp, maxSpeed, staleFade on CubePoseSubscriber (planned in Dev Documentation/CUBE_PERCEPTION_DEV.md).
  • Per-bin acceptedClasses[] for true colour-specific sorting.
  • Direct service call from TaskConfigPanel into Subsystem 2's /holoassist/pick_cube_to_bin.
  • Replace the hard-coded 192.168.0.101–110 ROSAutoConnect range with an Inspector setting.
