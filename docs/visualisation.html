Quick Start

Get the XR scene running

Required hardware

  • Meta Quest 3 headset, paired controllers, charged. Developer mode enabled.
  • USB-C cable for the Quest (build and run from Editor).
  • Linux laptop running Ubuntu 22.04 with ROS 2 Humble installed.
  • Any camera (RealSense D435i, UVC webcam, or laptop webcam) for AprilTag cube perception.
  • Printed 36h11 AprilTags on 40 mm cubes (tag IDs 10–33, four cubes). See the perception docs.
  • UR3e + OnRobot RG2 on the robot router (192.168.0.194) or URSim in Docker (192.168.56.101).

Required software

  • Unity 6.3 LTS (6000.3.9f1) with Android Build Support (OpenJDK + SDK + NDK).
  • Meta XR SDK 85.0.0 and all packages listed in Software stack — installed via Unity Package Manager on first open.
  • ROS 2 Humble + the project's ros2_ws built (colcon build --symlink-install).

Step 1 — Clone & open the Unity project

git clone git@github.com:John-A-Chen/HoloAssist.git cd HoloAssist && git checkout demo

Open Unity/My project/ in Unity Hub. The first import takes several minutes.

Step 2 — Open the demo scene

In the Project window navigate to Assets/Scenes/SampleScene.unity and open it. This is the only scene used for the demo.

Step 3 — Start the ROS side

# Fake hardware + default perception, MoveIt, dashboard ./scripts/launch.sh # OR — URSim + full stack ./scripts/launch.sh --robot-ip 192.168.56.101 --fake-gripper

Note the WiFi IP printed by the launcher — this is what Unity needs.

Step 4 — Connect Unity to ROS

In Unity Editor open Robotics → ROS Settings. Set ROS IP Address to the laptop WiFi IP from Step 3, and ROS Port to 10000.

On the robot router subnet (192.168.0.x) the in-scene ROSAutoConnect component will discover the host automatically. On other networks, disable it and enter the IP manually.

Step 5 — Deploy to Quest 3

  1. Connect the Quest to the laptop via USB-C, accept "Allow USB debugging" inside the headset.
  2. Unity → File → Build Profiles — ensure Android is the active platform.
  3. Click Build And Run. The APK installs to the Quest and launches.

What success looks like

  • Quest passthrough shows the physical room with a UR3e holographic twin anchored at the trolley.
  • Cube holograms appear within 1–2 seconds of pointing the camera at a printed cube face.
  • The RobotHUD floats in front of the operator showing mode, joint angles, and EE pose.
  • Holding the left primary button (X) opens the radial menu for mode switching.
  • Right stick moves the arm; right trigger drives the gripper.
Purpose & Role

What this subsystem owns

Subsystem 4 is the operator's window into HoloAssist. The Quest 3 scene is rendered here. S4 is responsible for everything in that scene except the digital twin and manual control core — those are owned by Subsystem 3 (Nic). S4 anchors S3's twin in the workspace and wraps it with cube and bin holograms, floating panels, a radial menu, the task/sorting UI, environment themes, and the passthrough toggle.

What the operator sees

  • A live UR3e digital twin + ArticulationBody joint mirroring Subsystem 3 (Nic)
  • AR cube holograms at positions detected by perception (relayed on /holoassist/unity/cube_N_pose).
  • A floating RobotHUD with mode, joint angles, EE pose, EE lock, and gripper state.
  • A grab-and-place RobotInfoPanel with full diagnostic readout.
  • A RadialMenu on the left primary button: mode switching, passthrough toggle, environment cycling, task control, confetti, etc.
  • BinDetector trigger zones + BinStatusPanel counter; TaskTracker scores correct vs wrong sorts.
  • PassthroughToggle swaps between MR passthrough and full VR skybox.
  • EnvironmentCycler swaps decorative theme roots (Portal Chamber, grass, open room).

How S4 supports the other subsystems

  • Perception (S1, John) — S4 visualises cube poses from S1. Cube hologram smoothing, jitter rejection, and persistOnTagLoss are owned here so perception jitter doesn't ruin the AR experience.
  • Autonomous (S2, Oliver) — The TaskConfigPanel is the operator entry point. Task mode drives how completion is scored; ObjectClass tags on perception-spawned cubes flow into TaskTracker.
  • Digital Twin + Manual Control (S3, Nic) — Nic owns the URDF, ArticulationBody hierarchy, JointStateSubscriber, RobotBasePlacer, and RobotController. S4's radial menu, EE lock, sub-mode toggle, and gripper trigger are the UI layer that calls into Nic's controller.

Main Scripts

Key script reference

Key fields, failure modes, and wiring notes for the most critical scripts.

CubePoseSubscriber

Path
Assets/Scripts/CubePoseSubscriber.cs
Attached
Dedicated GameObject (named CubePoseSubscriber)
Responsibility
Subscribes to {topicPrefix}/cube_N_pose for N=1..cubeCount; transforms pose into Unity space relative to robotBase; spawns and animates a prefab per cube with smoothing, averaging, outlier rejection, and optionally tags spawned cubes with ObjectClass for the task system.
Key fields
topicPrefix (default /holoassist/unity), cubeCount (4), robotBase (Transform — MUST be set), cubePrefabs[], poseTimeout (3 s), persistOnTagLoss (preferred: true), smoothing (0.5), useAveraging (true), tagSpawnedCubes, cubeClassNames[], cubeIsGood[]
Breaks if
robotBase unset — cubes spawn at world origin. Wrong topicPrefix — no messages received. Check /holoassist/unity/cube_N_pose and the ROS-TCP connection when cube holograms do not appear.

RobotHUD

Path
Assets/Scripts/RobotHUD.cs
Attached
"RobotHUD" GameObject
Responsibility
Floating gaze-following HUD. Subscribes to /joint_states directly as a self-heal; builds a TextMeshPro panel showing mode / sub-mode / joint angles / EE pose / EE lock / gripper / passthrough / TF state.

Goal: Standalone APK

Shipping as a Meta Quest 3 APK

The other HoloAssist subsystems integrate existing ROS 2 packages — ur_robot_driver, MoveIt 2, apriltag_ros, ROS-TCP-Endpoint. The XR Visualisation subsystem is different: it had to be built from scratch in Unity. There is no off-the-shelf package for spatial AR teleoperation on a collaborative robot. This is the piece that had to be authored.

The end goal is a standalone APK deployed directly to a Meta Quest 3 headset — no tethered PC required for the Unity side. Currently the app sideloads via adb install. A future release will target Meta App Lab or open distribution so any team with a Quest 3 and a ROS 2 system can deploy it in minutes.

Known Issues

Troubleshooting

  • Quest can't connect to ROS
    Both Quest and laptop must be on the robot's dedicated router (192.168.0.x subnet). ROSAutoConnect scans IPs 101–110 on port 10000. If auto-discovery fails, manually set the laptop WiFi IP in Unity → Robotics → ROS Settings.
  • Cube holograms not appearing
    Verify with ros2 topic echo /holoassist/unity/cube_1_pose --once, confirm Unity is connected to ROS-TCP-Endpoint, and check CubePoseSubscriber.robotBase in the Inspector.
  • ros_tcp_endpoint crashes on reconnect
    Known race condition in v0.7.0 (InvalidHandle exception). Restart the endpoint after every Unity Play/Stop cycle: ros2 run ros_tcp_endpoint default_server_endpoint.
  • Digital twin not responding to joint states
    Both forward_velocity_controller and finger_width_controller must be active. Run ros2 control list_controllers. With URSim, External Control must be playing on the teach pendant.
  • EE pose rows always zero in RobotInfoPanel
    /tcp_pose_broadcaster/pose is only available when the real robot or URSim is connected and running. With --fake hardware, the EE rows will remain at zero — this is expected.
  • Radial menu items missing after scene rebuild
    RadialMenu Inspector references were cleared when the scene was rebuilt. Re-run Tools → HoloAssist → Setup All UI Features to rewire all subsystem references automatically.
  • Bridge buffer overflow / lag with headset stream
    HeadsetStreamPublisher adds significant bandwidth. Disable the component on the Quest side if the ROS bridge becomes unstable. The dashboard will lose the headset tab view but all other features remain working.
  • Task scoring incorrect in OneOfEachClass mode
    CubePoseSubscriber.tagSpawnedCubes must be true and cubeClassNames[] / cubeIsGood[] must be populated. Without this, all cubes score as class "default" and the OneOfEachClass logic cannot distinguish correct from incorrect sorts.
