Overview

What this subsystem does

The teleoperation subsystem lets an operator control the UR3e arm and OnRobot RG2 gripper using Quest 3 XR controllers (thumbsticks, buttons, and analog triggers). Unity C# scripts compute joint velocity commands via Jacobian-based kinematics and publish them over the ROS-TCP-Endpoint bridge to the ur_onrobot combined driver.

The Quest app auto-discovers the ROS bridge via TCP scanning (ROSAutoConnect.cs scans 192.168.0.101–109 on port 10000). All devices share a dedicated robot router on the 192.168.0.x subnet for stable, low-latency communication.

Three control modes are cycled via Menu button: RMRC (Cartesian velocity with translate/rotate sub-modes), Direct Joint (individual joint jogging), and Hand Guide (controller position tracking with Jacobian IK). The right index trigger controls the gripper analog (0–100%) in all modes.

Lead: Nicholas Sabatta  ·  Client: Unity 6 + Quest 3 (C#)  ·  Bridge: ROS-TCP-Endpoint :10000  ·  Driver: UR_OnRobot_ROS2

How to Run

Get started in seconds

Once the system is launched, enable teleoperation control via the dashboard. Put on the Quest 3 headset, pick up the controllers, and use the radial menu to select your control mode and start moving the robot. That's it.

Pipeline

Controller input to robot motion

01

XR Controller Input

Quest 3 controllers read via Unity Input System — thumbsticks, A/B/X/Y buttons, grip, and analog index trigger. RobotControlActions.inputactions binds all inputs.

›
02

Kinematics & Control

RobotController.cs maps input to velocity commands. RMRC uses UR3eKinematics.cs (DH forward kinematics + geometric Jacobian + DLS pseudoinverse). Hand Guide uses proportional control + Jacobian IK.

›
03

ROS-TCP Bridge

Joint velocities published as Float64MultiArray via ROS-TCP-Connector at 50 Hz. ROSAutoConnect.cs handles IP discovery by TCP scan on the 192.168.0.x subnet.

›
04

UR3e + RG2 Execution

The ur_onrobot driver receives velocity commands on forward_velocity_controller and gripper width on finger_width_controller. Digital twin mirrors via /joint_states.

Control Modes

Intuitive, user-focused control

The teleoperation system is designed to be simple and intuitive. An operator can pick up the Quest 3 controllers and start moving the robot immediately — no training required. All mode switching, sub-mode toggling, and feature activation is handled through a radial menu on the controller, keeping the interface clean and discoverable.

The gripper is always available on the right index trigger regardless of which mode is active, so pick-and-place workflows feel natural. The EE lock-down (activated by clicking the left thumbstick) keeps the gripper pointing straight down automatically, making object pickups effortless.

ModeInputDescription
RMRC TranslateBoth sticksJacobian-based Cartesian velocity control. Right stick = XY (forward/back, left/right), left stick Y = Z (up/down), left stick X = yaw. Radial menu toggles to Rotate.
RMRC RotateBoth sticksDirect wrist joint control. Right stick Y = wrist 1 (pitch), right stick X = wrist 2 (roll), left stick X = wrist 3 (yaw). Radial menu toggles back to Translate.
Direct JointRadial menu + right stickSelect joint (1–6) via radial menu. Right stick Y jogs the selected joint with proportional velocity control.
Hand GuideRight gripHold grip to engage — controller 3D position tracked and mapped to end-effector via proportional control + Jacobian IK. Release to stop. The most intuitive mode for new operators.
GripperRight triggerAnalog 0–100% in all modes simultaneously. Squeeze to close, release to open. Feels like a natural pinch.
EE Lock-DownLeft stick clickToggle — angular Jacobian drives tool Z-axis to point straight down. Keeps the gripper oriented for pickups automatically.

Dashboard

E-stop & debug console

A Python/PyQt5 dashboard (main.py + ros_interface.py) runs on the laptop. The e-stop column is always visible on the right. Six tabbed screens provide real-time telemetry.

E-stop sequence: burst-publishes zero velocity (10x), then continuous zeros at 50 Hz, deactivates controllers. Resume requires a 5-second hold on the yellow button, followed by a 1-second cooldown.

Session Logging

Automatic telemetry & session capture

Every teleoperation session is automatically logged by SessionLogger.cs. It tracks mode switches, per-mode durations, session time, and e-stop events — publishing live JSON telemetry to /session/status at 2 Hz and discrete events to /session/events.

When the operator ends a session, the full session log is saved as a JSON file on the Quest. The dashboard independently saves its own log (including Unity session data and e-stop count) to ~/holoassist_sessions/ on the laptop. This enables post-session analysis, performance comparison, and quantitative evaluation of teleop vs autonomous sorting.

Known Issues

Troubleshooting

  • Quest can't connect to ROS
    Both Quest and laptop must be on the robot's dedicated router (192.168.0.x subnet). ROSAutoConnect.cs scans IPs 101–109 on port 10000. If auto-discovery fails, manually set the laptop WiFi IP in Unity ROS Settings.
  • Arm unresponsive to controls
    Both forward_velocity_controller and finger_width_controller must be active. Run ros2 control list_controllers to check. With URSim, External Control must be playing on the teach pendant.
  • ros_tcp_endpoint crashes on reconnect
    Known race condition in v0.7.0 (InvalidHandle exception). Restart the endpoint after every Unity Play/Stop cycle.
  • Teleop lag / jitter
    Some lag is inherent in the ROS round-trip (Unity → ros_tcp_endpoint → controller → /joint_states → Unity). Output smoothing (60ms low-pass) reduces jitter. EE lock-down uses 2° dead zone to prevent oscillation.
